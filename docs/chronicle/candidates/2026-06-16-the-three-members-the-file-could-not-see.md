## The record

A sale engine cannot see the members who joined before it. It has to be told, once, at deployment: how many seats are already taken, and a single fingerprint — a Merkle root — of the exact list of addresses holding them. Both values are set when the engine is deployed, read from a parameter file prepared beforehand. Right, and a returning member is recognized and keeps their number. Wrong, and the engine has no way to know that person exists.
On 2026-06-16 the protocol was preparing to replace the sale engine then live at 0x0b883Ff08fE78146E4d81237dD7aE8A2a6502b48. The replacement was needed for a separate reason, which is not what this record is about; this record is about what the replacement was almost built from. The parameter file the deployment script would read unless told otherwise — contracts/script/deploy-params.json — was marked as not provisional and carried an internal note declaring its two identity values canonical. They were a count of two, and the fingerprint 0xae75ae2077570c7bd09d95cc142e283cfa73fc9e263c2debf1ba3403457474ff.
Those values were correct when they were made. The scan behind them is timestamped 2026-06-15T15:16:30Z, and at that moment the live engine had sold nothing. Four hours and forty-seven minutes later, at 2026-06-15T20:03:33Z, its first member bought a seat — five dollars in USDC, transaction 0x46b38df9403fbb1b1e0f78b2def6d1d83f34ed18db1a055690db2d9290dae0ae — and the engine wrote seat #3. Two more bought on the morning of 2026-06-16 itself, at 10:35:36Z and 10:38:14Z, taking seats #4 and #5. The file did not change. Nothing happened to it. It simply stopped being true.
That fingerprint commits to exactly two addresses and to no others: rebuild it from the two earliest members' addresses alone and it reproduces bit for bit. So an engine deployed from that file would have carried a commitment naming two people while five held seats. The two earliest were inside it and would have been recognized normally. Seats #3, #4 and #5 were outside it. Three of the five, not all five. The report written that day states the consequence in its own conflict register: reusing that root would "fail to recognize the 3 V2a members", and they "could be re-issued seats (duplicate identity = the one irreversible mistake)" — could, not would, because a member the engine cannot recognize is only issued a second seat if they buy again. A second report filed later the same day lists the file among the live blockers, "V1-ONLY and dangerous if used by accident", and names what made the danger structural: it was the deployment script's default path, so any command that did not explicitly name another file would read it silently.

## What the protocol did

Nothing was deployed from it. The decision to re-snapshot across both sale contracts rather than reuse the old artifact appears in that same conflict register as a Founder-approved item, and the row carrying it also states what the alternative would have cost — the counterfactual was written down beside the instruction, not discovered after it.
The new roster was built as the union of both sale contracts' purchase events, sorted oldest-first by block and by position within the block, reduced to each buyer's first appearance, then numbered from one — the same ordering rule the protocol's own live purchase feed already used, so the seat numbers the live engine had issued were preserved rather than reassigned. It produced five members and a new fingerprint, 0xa1f2ed106c6d87372d99256765fcbad8c150441913d7bf0ea51908665f718c49, which likewise rebuilds exactly from those five addresses.
The exporter was written to refuse rather than guess. Before emitting anything it checks that its own count of distinct members equals the live engine's member count at the same block, that every first-time buyer's derived number equals the number the engine actually issued, and that every repeat buyer has a strictly earlier first appearance. All three passed. In the report's words: "it never emits a snapshot that could mis-number a seat."
Then the path itself was closed. The deployment script stopped hard-coding the default file, began logging the file it had loaded, and required the operator to declare the seat count and the fingerprint independently, reverting on any disagreement between the declaration and the file. Three dry runs proved it, one of them the exact near-miss: the default file, a correct declaration, and a revert that prints the name of the file it read. By that evening those two declarations were mandatory for any deployment not marked as a rehearsal.
The replacement engine went live the next day at 0x507E9c9C365a865F2A2b94DA9E12ccCC2bBeB88b, in block 88193183, 2026-06-17T00:58:29Z. It carries the count five and the merged fingerprint. The corrected values went into a separate file; contracts/script/deploy-params.json still reads two.

## Why this is recorded

Nothing happened. No transaction was sent from that file, no member lost or gained anything, no money moved. This is a fault that never acted.
It is recorded because of what the protocol treats as irreversible. Seat identity is the one thing it cannot take back: once an engine issues a second seat number to someone who already holds one, no later act removes it — the engine will not un-issue a seat, and the chain will not forget. That is not hypothetical here. Twenty-six days later, on 2026-07-12, the same harm arrived by a different route: a historical member who had not claimed their seat purchased through the engine then live and was issued a second one. This register carries it as "The duplicate seat" — one person, two seat numbers, permanent. There the commitment was correct and the member had simply not claimed. Here the commitment itself would have been wrong, and three members would have stood exposed to it instead of one.
So the near-miss is recorded at the same weight as the event that landed. A register publishing only the mistakes that reached the chain would be asking its reader to take the protocol's word for everything it caught in time — the one part no reader can check. This part can be checked, because the evidence was left where it fell: the file that would have been wrong is public and still says two, the engine that shipped says five, and each fingerprint rebuilds from its own list of addresses and from no other. The distance between two and five is the whole record.
